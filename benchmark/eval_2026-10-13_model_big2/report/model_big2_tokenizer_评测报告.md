> **核心发现**
> 1. 与第一代 `model_big` 相比，二代在 4 倍语料（3.28 GB → 14.3 GB）与 3 轮续训后，各项指标基本原地踏步：整体 BPT 3.5992 vs 3.6036（-0.12%，即略差），中文还原率同样为 85/200 行失败。

### 1.3 指标定义（依 `eval_metrics.py` 源码）

| 指标族 | 定义 | 方向 |
|---|---|---|
| 编码效率 BPT | 字节数 / token 数（bytes per token），分语种与整体统计 | 越高越省 token |
| 还原率 roundtrip | 每语种取前 200 行，逐行 encode→decode 后与原字节逐字节比对，统计失败行数 | 失败数越少越好 |
| 稳定性 stability | 每语种 100 句施加 3 类扰动（大小写互换 / 随机拼写错误 / `\n`↔`\t`），比较原 token 序列的 Jaccard 相似度 | 越高越稳 |
| 吞吐 throughput | 最大语料文件整体 encode/decode 计时（tokens/s），含模型加载 ms | 越高越快 |
| OOV / 字节回退 | 依赖 `.model` + sentencepiece 统计未登录率；`.tkm` 无此输出（null） | 越低越好 |
| TokEval §3.4 | `utf8_completeness` 多字节字符被完整编码进单 token 的比例；`char_split_rate` 唯一多字节字符中其 UTF-8 编码未出现在任何 piece 中的比例（=整字覆盖缺口）；`boundary_crossing_rate` 跨字节边界 token 比例 | 完整性越高越好，另两项越低越好 |
| TokEval §3.5 | `digit_boundary_f1` 数字串切分边界 vs 右对齐三元组理想边界的 F1；`digit_split_variability` 同一数字串切分不一致程度；`operator_isolation` 操作符单独成 token 比例 | F1/隔离度越高越好，变异性越低越好 |

### 1.4 口径与可比性声明

- **实测方式**：本项目三款 `.tkm` 通过 `tok-cli-fast.exe`（C++ 进程级）实测；厂商基线通过其原生 Python 绑定（`tokenizers` / `tiktoken`）加载真实权重实测。
- **基线可信度校验**：用厂商原始 tokenizer 在评测语料上复现其 `*_eval.json` 的 token 数，15 组中 12 组完全一致，3 组（code 语料）偏差 -0.42% ~ -0.44%，见表 1-4 之外的校验记录（`temp\indomain_results2.json` → `validate`）。故厂商基线数值可直接横向比较。
- **不可横比项**：吞吐（进程级 CLI vs 原生内存批处理）、OOV（`.tkm` 输出 null）、模型加载耗时。这三项仅在本项目三代模型之间可比。
- **字节回退替代测量**：因 `.tkm` 无 `byte_fallback_rate` 输出，本次通过逐 token id 统计负 id（字节 token）占比获得等效指标（见第三章）。

## 三、关键差异根因分析

### 3.1 中文压缩效率低：字节回退主导，整字覆盖不足

对真实中文语料逐 token 统计（883,092 tokens）：

| 指标 | model_big2 | model_big | model_256k |
|---|---|---|---|
| 字节回退 token 占比（真实中文） | 42.88% | 42.86% | 67.5% |
| 字节回退 token 占比（合成中文） | 36.36% | 36.28% | — |
| 高频 token 前列 | `<byte 229/230/232/231>` 占 4.17%/2.68%/2.63%/2.41%，前 12 名中 8 个是字节 token | 同左，字节占比几乎一致 | — |
| 收录整字 piece 数 | 968 | 978 | 427 |
| 整字覆盖（不同汉字，共 4,113 个） | 22.95% | 22.83% | 10.38% |
| 整字覆盖（按出现频次加权） | 79.31% | 79.31% | 67.28% |
| 中文词表利用率（真实语料 262,144 词表） | 3.09%（8,093 个 id） | 2.99% | — |
| 中文词表利用率（合成语料） | 0.26%（692 个 id） | 0.25% | — |

**机理**：一句话解释——**常用字有整字 piece，长尾汉字全靠 3 个单字节 token 拼**。968 个整字 piece 只覆盖 22.95% 的不同汉字，剩下约 77% 的汉字（长尾）必须走 byte_fallback，每个汉字消耗 3 个 token，直接把中文 BPT 拉到 2.48（0.85 汉字/token）。相比之下，厂商字节级 BPE 虽无整字 piece，但其 merge 表能把高频汉字与常用词合并为 1 个 token，实测 1.42–1.89 汉字/token（grok 4.127 / hunyuan 5.489）。

**另一个信号**：262,144 的词表在真实中文语料上只用到 3.09%，说明词表容量并未有效分配到中文，当前预算偏向英文与代码——这与英文指标领先、中文指标垫底的分布完全一致。

### 3.2 中文还原率失败：NFKC 归一化不可逆

受控实验（对照见 `temp\roundtrip_rootcause.json`）：

| 组 | 抽样 | 结果 |
|---|---|---|
| A 组：含 NFKC 可变字符的行 | 60 行 | **60 行全部还原失败** |
| B 组：不含 NFKC 可变字符的行 | 60 行 | 0 行失败 |

- 中文语料 `zh.txt` 共 80,694 行，其中 36,419 行（45.1%）含 NFKC 可变字符；评测抽样的 200 行中 85 行失败（42.5%），与 45.1% 的可变行占比吻合。
- 典型失败：原文"在武汉大会上**，**与会代表…"，解码后为"在武汉大会上**,**与会代表…"——全角逗号 U+FF0C 被 NFKC 折叠为半角 U+002C，解码端无法还原原字节。
- 英文/代码语料不含全角字符，故还原率为 0 失败。

**结论**：还原率失败与词表缺失无关，是 `normalizer=NFKC` 的单向归一化所致；历史 256K 版本与一代同为此问题（同样 85/200）。

### 3.3 历史 256K 报告的高分不可采信

| 语料口径 | model_256k | model_big2 |
|---|---|---|
| 合成评测语料（en/zh/code） | 7.397 / 7.996 / 7.232 | 4.589 / 2.483 / 4.110 |
| 真实域内语料 | 1.497 / 1.729 / 1.435 | 4.560 / 2.375 / 3.380 |

`model_256k` 在评测语料上达到 7.2–8.0 BPT（约为本模型的 1.8–3.2 倍，表面最优），但在真实文本上骤降至 1.4–1.7（不足 1 个 token 对应 1 byte，等同于逐字节退化）。同一模型在两个口径下相差 4–5 倍，只能解释为**评测语料与训练语料同源导致的记忆效应**，而非真实编码能力。

`eval_report_2026-10-10`（256K 报告）中的语言模型侧分数（perplexity 109.17 等）建立在同源语料之上，**不可作为本项目的对外基线或改进依据**。相比之下 `model_big2` 在两个口径下保持一致（英文 4.589/4.560，中文 2.483/2.375），泛化性良好——这是本次评测中最值得保留的优点。

### 3.4 数字与操作符切分的规范性缺口

- 数字：`digit_boundary_f1` 0.400 与 grok 持平（0.403），但 `digit_split_variability` 1.660 远差于所有厂商（0.000）。即同一数字串在代码中位置不同会被切成不同长度的 token 序列，对下游按位置对齐、语音/OCR 流式场景不友好。
- 操作符：`operator_isolation` 0.433，介于厂商字节级 BPE（0.167）与 grok / 256K 版本（0.967 / 0.983）之间。相比一代（0.367）改善 18.1%，但仍未达到把 `+ - * / = ==` 等稳定独立成 token 的水平。

## 四、结论与改进建议

### 4.1 结论

**相对第一代 model_big：基本持平，无实质收益。**
语料规模扩大 4.36 倍、续训 3 轮后，整体 BPT 3.5992 vs 3.6036（-0.12%），还原率同样失败 85/200，整字 piece 由 978 个降至 968 个、覆盖广度未改善。唯一可见改进在操作符隔离（0.367 → 0.433，+18.1%），但数字切分变异性反而变差（1.587 → 1.660）。**训练规模的增长没有转化为词表质量提升。**

**相对厂商基线：分语种分化严重，中文是系统性短板。**
- 英文：合成语料上领先 19.8%–25.0%，但真实语料上仅持平（4.560 vs 4.513–4.770，互有胜负）。
- 代码：合成语料上与厂商同档（差距 ≤6%），真实语料上落后 9.2%–20.5%。
